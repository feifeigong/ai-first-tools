## 代码中的具体原因

- `ResetNewsService.ParseFeed` 只枚举 `tweets`，无历史分页/补采；30 天只是保存上限，不表示已经采全 30 天。
- `Classify` 不接受 `Day N/ Reset`、`Le limit reset`、`All propagated`、`Done`、`Done and dusted` 等实际措辞。候选在官方核对前就被丢弃。
- `TimingReply` 漏掉 `Landing`；完成短句也没有带上下文的识别入口。不能仅增加全局 Done 关键词，否则会误把普通发布当重置完成。
- 没有 banked 类型；Day 3 完整原文还会被普通预告规则误判。应区分直接重置、预告、发放重置卡。
- 每轮最多核对最新 12 个候选，没有历史游标。当前快照未触及该上限，但长期不能把此路径当完整历史查询。
- 日历只展示服务提供的记录，改变月历布局并没有解决上游覆盖缺口。

## 待修范围

1. 为历史建立有界补查和持久进度，先用公开档案发现原帖编号，再逐帖核实；不信任第三方完成标记或观察时间，不放宽截断/作者/正文检查。
2. 按原帖及明确关联的上下文识别预告和完成，覆盖这些真实措辞；独立短句无法关联时保留待核实，不能猜配对。
3. 加入独立的发卡类型和中文显示；各阶段正确去重，历史补齐不批量弹旧通知。
4. 用这些公开样例构建隔离回归，同时保留愿望、问句、否定、非重置发布、截断、作者冲突等反例；对照清单验证覆盖率，而非只验接口可读和少量理想句。
