# Windows 与 Mac 同次发布

自动发布入口是 `.github/workflows/release-pair.yml`。只有 `master` 上 `.github/release-pair.json` 的变更触发；普通源码或文档提交不会自动公开版本。

发布请求明确指定 Windows 版本、Mac 预览版本、已审核的说明文件、`publish: true` 和正整数 `attempt`。它们必须与源码版本一致，整个流程固定到该次推送的提交；如果 `master` 已前进，准备或公开步骤会拒绝旧请求。

流程依次执行完整 Windows checks、Windows 安装包和两个 Mac 架构的原生构建。全部成功后，先验证本地完整报告和资产，再创建同一源码提交的轻量标签和草稿；已有标签不移动，已公开同名版本不覆盖。复用原有 stage/verify 脚本逐项下载并核对 Windows 3 个、Mac 23 个资产后，才允许最后的公开步骤。

公开步骤再次核对同次运行的验证记录、标签、release ID、完整文件集合、字节数与 SHA-256。GitHub 不支持两个 release 的原子公开，因此先公开 Mac 预览，再公开 Windows 正式版本。如果第二次操作失败，`release-pair-publication` 产物会保留已确认状态；重跑该次运行的失败公开任务，只允许跳过仍与验证记录完全一致的已公开项，不重新上传或覆盖它。

在尚未创建标签前，可增加 `attempt` 明确发起新的构建。标签创建后，应重跑原来的工作流任务，不能通过移动标签把另一次提交伪装成相同构建。新的发布请求不能覆盖已公开版本。

独立 Windows/Mac 构建工作流现在只构建和上传 CI 产物，不再自动暂存草稿。原 `stage-verified.yml` 保留手动暂存与独立核对能力；正常双平台发布使用新入口。Mac 普通推送会识别同次显式发布请求，避免重复执行昂贵的原生构建；paired 调用通过布尔输入确保实际构建，不依赖调用者的事件名称。

编排测试使用合成报告和模拟 GitHub，禁止真实子进程。原生打包沿用隔离、未登录配置的版本/参数/历史读取检查，不提交模型任务；本流程不需要个人 token 或用户的 Codex 认证。
